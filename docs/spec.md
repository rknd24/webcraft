# WebCraft 仕様書（たたき台）

## 目的
Web技術の基礎を、自分で問題を作る・4択で解く・間違えたところを復習する、の繰り返しで身につける。
このプロダクトの目的は「作る過程でWeb技術と知識を学ぶこと」で、完成後に使い続けることは目的にしない。

## 出題の考え方
- 知識が定着するのは作問する時なので、自分で問題（問題文・選択肢・正解・解説）を作り、4択で出題する
- 割り切り：解く時は問題文から答えを思い出せてしまい、理解の確認としては弱い
- AIによる出題・採点は作らない。その分の時間をDB設計・認証・トランザクションに使う
- 判断の経緯は `docs/adr/001-4択形式にする.md`

## 最初の範囲（カテゴリ）
- HTTP・ネットワーク
- ブラウザとフロント
- API・バックエンド
- DB
- 認証・セキュリティ

カテゴリはデータとして持ち、後から追加できるようにする（OS・インフラなどは後で）。

## MVP（スプリント1〜2）
- 問題を登録できる（問題文・選択肢4つ・正解・解説・カテゴリ）
- カテゴリを選ぶと、その中から問題が1問出る
- 4択で答えると、正誤と解説が見られ、結果を記録できる

## やらないこと（今は）
- ログイン・ユーザー管理（スプリント3で追加）
- 間違えた問題の自動出し直し（スプリント4で追加）
- AIによる出題・採点、記述式（ADR 001で見送り）

## ユーザーストーリー
- 学習者として、カテゴリを選んで問題を解きたい。苦手な分野を集中して学びたいから
- 学習者として、解答後に解説を見たい。なぜその答えになるのかを理解したいから

- 解答履歴に何を残せば、後で「苦手な問題の出し直し」に使える？

気づいたこととしてN対Nの関係は中間テーブルを挟むのが定番らしい。それが何故かはわからない　プレースホルダとは？
DBをユーザー専用にするのは技術的には可能ではあるが、構造の変更を全部に適用する手間や接続の管理が大変。

変わらないものは列に置くというのは1対1だと正しい

### 設計メモ：選択肢テーブルで何を間違え、どう気づいたか
**最初のER図**
- `option` テーブルに `option1〜4` の列を並べ、1行を「1つの問題」とした。
- 理由は「基本変わらないものは列に置く。増やすときは結合する」。

**何が違っていたか**
- 1行が1つの問題を表すと、問題と選択肢は1対1になる。別テーブルにした意味がなく、選択肢を問題テーブルの列に持つ案と実質同じになる。
- 拡張したかったのは「問題の数」ではなく「選択肢の数と中身」だった。5択にしたくなると、行を足すのではなく列を足す変更になり、既存の全問題に影響する。
- 線では問題と選択肢をつないでいたが、`option` に `question_id` の列がなく、「どの問題の選択肢か」が図に表れていなかった。

**気づいたきっかけ**
- 「その行は何を表すか」を一言で言う。「選択肢1つ」と言えなかった。
- 「5択になったら？」「シャッフルしたい」「正解はどの列？」と、変更が来たときを考える。
- データを数行書いてみる。同じ `question_id` が4回出てくるのが、正しい形だと見えた。

**正しい形**
- `option`：`option_id`、`question_id`、内容、正解（boolean）。1行が選択肢1つ。
- 選択肢を足すときは、行を1つ追加するだけ。

**考え方の型**
1. 「1つの◯◯に、いくつの△△があるか」を言葉にする。「1つの問題に選択肢が複数」なら1対N。
2. 1対Nなら、Nの側に、1の側のIDを列として持たせる。
3. 「その行は何を表すか」を一言で言う。言えない、または `option1, option2…` と番号付きの列を作りたくなったら、行にすべきサイン。
4. 同じ情報を2か所に持たない。解答履歴が問題IDを持たないのは、このため。

**未解決**
- 解答履歴・苦手テーブルの列と線の見直し（履歴は選択肢IDと日時、苦手はユーザーと問題の中間テーブル）。
- N対Nで中間テーブルが要る理由、プレースホルダ（バインド変数）とは何か。
- カテゴリをDBにするかどうか（トレードオフは検討済み。決定はまだ）。

自分の言葉でDB設計
二つの間の共通の動詞を考えて双方向において0，1，多どれが当てはまるかを考えて、それに対して最後どうアプローチをかけるか考えるということ
1対NならNのテーブルに1の列を
N対Nなら中間テーブルを挟む

主キーはnullにならず重複しないもの
専用のID列を作るか、複数の列を組み合わせて、主キーにするか
